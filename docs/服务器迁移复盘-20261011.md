# 服务器迁移复盘：Windows+宝塔 → Ubuntu 裸机部署

> 2026-10-11 一次部署任务踩坑全记录。起因：把 Atlas 四阶段成果部署到线上 Windows 服务器，途中连环踩坑，最终演进为整个系统重装（Windows+宝塔 → Ubuntu 26.04 裸机 + systemd），一次迁移解决了所有旧架构顽疾。

## 一、事故时间线（踩坑清单）

### 1. 宝塔面板端口迁移后的连环锁死
- 用户收到"8888 端口有入侵风险"提示后改面板端口为 15241，随即登不上面板
- **根因**：改端口只改了面板监听，云防火墙（腾讯云轻量服务器）没放行新端口。旧 8888 规则还挂着但服务已不在，两头堵死
- **教训**：改服务端口的第一件事永远是同步放行防火墙（云安全组 → 系统防火墙两层都要查）

### 2. 宝塔安全入口导致部署脚本 404 风暴
- 面板开启"安全入口"后，不带入口串的所有路径一律 404，与 cookie 过期症状难以区分
- **教训**：宝塔 API 自动化必须先确认完整面板 URL（协议+IP+端口+入口串）；404 风暴先怀疑入口串，再怀疑凭证

### 3. 宝塔新版 API 与旧脚本全面失配
- 旧 `deploy_to_bt.py` 按老版面板写的端点，新版面板路径全变
- cookie 格式变化、`_csrf` 机制变化，逐个端点试错成本极高
- **教训**：依赖面板私有 API 的自动化极其脆弱，面板一升级全部重写。这是最终放弃面板路线的直接原因之一

### 4. Python 3.8 语法炸弹（服务 502）
- 部署"成功"但整站 502：waitress 没起来
- **根因**：服务器 Python 3.8.6，新代码 memory.py 用了 `str | None` 注解（3.10+ 语法），import 崩溃
- **更深的坑**：部署 bat 用 `start /MIN` 异步启动，不等待服务就绪就写 DONE，造成"部署成功"的假象
- **教训**：① 本地开发环境版本永远高于生产环境，合并前必须确认目标环境版本；② 部署脚本必须同步等待健康检查（curl 探活）而非异步撒手

### 5. 宝塔面板防御拦截脚本流量
- urllib 无浏览器指纹的请求被面板 WAF 拦截（404 假响应），换 curl 重放浏览器请求头才通过
- **教训**：面板自带防护会误伤自动化，这是无面板架构的又一个加分项

### 6. GitHub 直连不可用 + 国内镜像全灭
- 北京国内服务器直连 github.com 极慢，git clone 假死（挂 10+ 分钟无进展）
- 逐个测国内加速镜像：ghproxy.com 已死（域名超时）、gh-proxy/ghfast 对私有仓库返回 401/404（公共代理无法代理私有仓库）、gitclone.com 502
- **教训**：私有仓库 + 国内服务器 = 公共加速镜像全走不通（镜像不替你认证）。不要在镜像上耗时间

### 7. 最终解法：绕开 git，本地打包直传
- `git archive` 打包（24M）→ pscp 上传（8MB/s，3 秒）→ 服务器解压
- 不依赖 GitHub 链路，不依赖镜像，几秒钟完成
- **教训**：国内服务器拉 GitHub 是老大难，直传永远是最短路径。大文件 scp 内网速度远超任何中转

### 8. SSH 自动化的交互陷阱
- OpenSSH 客户端交互式密码提示无法在后台命令中输入，命令假死
- plink 首次连接要交互确认主机指纹，`-batch` 模式下直接失败
- **解法**：plink/pscp（支持 `-pw` 命令行密码）+ 首次 `echo y` 接受指纹后用 `-hostkey SHA256:xxx` 直连
- **教训**：Windows 上做 SSH 自动化，plink/pscp 比原生 ssh 省事得多；指纹固化后一律 `-batch` 防假死

### 9. PowerShell 5.1 语法兼容
- `&&` / `||` 链接符不可用（需 PowerShell 7），嵌套引号转义极易出错
- **解法**：复杂命令写成脚本文件（scp 上传后执行），不在命令行里拼长命令；本地 PowerShell 用 `;` 串联

### 10. pscp 递归上传的目标目录
- `-r dir host:/tmp/newdir` 在目标不存在时失败（failure）
- **解法**：先 SSH mkdir，或传到已存在的父目录（`-r dir host:/tmp/` 会保留原目录名）

## 二、架构决策与依据

### 为什么放弃面板（宝塔/1Panel）
- 对 agent 自动化，SSH + shell 才是第一公民；面板 API 是黑盒，升级即碎
- 宝塔吃 400-800M 内存，Windows Server 底座再吃 1-1.5G，小内存机器窒息
- 面板防御会拦截自动化流量，反而添乱

### 新架构
```
Ubuntu 26.04 LTS（2026-04 发布的 LTS，支持到 2031）
├── Python 3.14 venv（/opt/lykie/.venv）
├── waitress 127.0.0.1:5000（4 线程）
├── systemd lykie.service（Restart=always, 3s 拉起, 开机自启）
├── Nginx :80 反代（/static/ 直接服务 + 7d 缓存，client_max_body_size 20m）
└── 防火墙仅开 22/80/443
```
- 内存从 ~2G 降到 475M，可用 1486M
- 服务管理：`systemctl restart lykie`；日志：`journalctl -u lykie -f`

### 新部署流程（deploy_to_bt.py 已退役；2026-10-30 修订：补 --prefix 与部署验证）
```
1. git -c core.autocrlf=false archive --format=tar.gz --prefix=Lykie/ -o lykie_code.tar.gz main
2. scp/pscp 上传 tar 到 /tmp/
3. 服务器解压覆盖 /opt/lykie：tar -xzf /tmp/lykie_code.tar.gz --strip-components=1 --exclude=data --exclude=.venv --exclude=.env
   （--prefix 与 --strip-components=1 必须成对出现；--exclude=data 必须带：data/ 下有 git 追踪的
    遗留文件 bank.json/mastery.json/lykie_state.json 等，不带会把服务器端版本覆盖回 git 版本）
4. systemctl restart lykie
5. 验证：sleep 几秒后 curl 探活拿 200，并抽查目标文件 mtime/md5——服务活着 ≠ 代码更新
```

## 三、沉淀的规则（下次直接照做）

1. **生产环境版本先行确认**：部署前 `python3 --version`，3.8 环境必须全仓扫 `str | None` 类语法（本次已给所有模块加 `from __future__ import annotations`，新代码也保持这个习惯）
2. **部署脚本必须有同步健康检查**：重启后 curl 探活拿到 200 才算完成，杜绝异步假成功
3. **私有仓库不要试国内镜像**：直接本地打包 scp。公网 GitHub 只用于本地 push 备份
4. **SSH 自动化用 plink/pscp**：`-pw` 传密码、`-hostkey` 固化指纹、`-batch` 防交互假死
5. **复杂远程命令写脚本文件上传执行**，不在命令行拼转义地狱
6. **改端口必改防火墙**，删规则跟着服务走（旧端口规则及时清理）
7. **数据备份三处核对**：users 数据（唯一不在 git 的）、.env（gitignore 屏蔽）、代码（git）。迁移前逐项确认下载并验证解压
8. **重装系统选 LTS**：Ubuntu 26.04 LTS 支持 5 年，Python 直接 3.14，旧版本兼容性问题不复存在
9. **连接信息与敏感凭证不入 git**：SSH 密码/密钥、API key 只存本地安全位置

## 五、2026-10-30 追加：直传部署踩坑（--prefix 缺失事故）

### 事故经过
- `git archive` 没带 `--prefix=Lykie/`，解压却用了 `--strip-components=1`：所有二级路径被剥掉首段，
  `static/reading.js` 散落到根目录、`static/lykie/*.png` 混进 `lykie/` Python 包目录……
  真正的目标文件一个都没被覆盖，服务一直在跑旧代码
- 更险的是当时 `systemctl is-active` 正常、探活 200——完全假成功
- 发现手段：部署后核对 md5，服务器与本地对不上 → `stat` 看 mtime（目标文件时间戳根本没变）
  才确认覆盖从未发生
- 修复：从同一个 tar 包在服务器端反推错位文件清单（`tar tzf … | awk -F/ 'NF>=2 {sub(/^[^\/]*\//,"")}'`），
  精确删除 194 个错位文件（`data/`、`.venv`、`.env` 全程未波及——git archive 不含它们），
  再带 `--prefix=Lykie/` 重新部署，逐文件 md5 验证与本地一致

### 新沉淀规则（接着上面 9 条）
10. `git archive` 的 `--prefix` 与解压的 `--strip-components=1` 必须成对出现（或都不用）——
    单独出现就是把所有二级路径剥错层的定时炸弹
11. 部署完成的判定 = 探活 200 + 目标文件 mtime/md5 核对，缺一不可；服务活着不等于代码更新
12. `core.autocrlf=true` 的本地仓，`git archive` 出的包是 CRLF；服务器要保持 LF 惯例就加
    `-c core.autocrlf=false`（先 `tr -d '\r'` 后比对 md5，确认只是换行符差异再决定是否重打）
13. 改 `static/` 下的文件必须同步 bump `templates/index.html` 里的 `?v=` 版本号：
    nginx 对 `/static/` 有 7 天缓存，浏览器也缓存同 URL，不 bump 用户拿不到新文件
14. waitress 重启后探活要留几秒就绪时间，先 sleep 再 curl，HTTP_000 不代表挂了
15. `git archive` 会带上 data/ 里被 git 追踪的遗留文件（bank.json、mastery.json、lykie_state.json——
    代码里就叫 LEGACY_BANK/LEGACY_LYKIE），解压必须 `--exclude=data`。本次没丢数据纯属侥幸：
    根文件运行时无人写入（mtime 全是部署时刻），真实运行时数据都在 data/users/<账号>/ 与
    users.json、qq_lykie.json 里——它们被 gitignore，天然不在包内
16. 数据同步「服务器→本地」的核对清单：users/ 每账号文件数 + 抽查 md5 + users.json 账号名单；
    secret_key 保留本地（换它只会让本地 cookie 失效）。备份用 `sudo tar`（部分用户文件属主
    是服务进程身份，ubuntu 直读会 Permission denied）

### 顺带确认
- 服务器部署通道：`ubuntu` 用户密钥登录（root 不通），免 sudo 可写 /opt/lykie；
  本机无 plink/pscp，原生 OpenSSH 的 scp/ssh 即可（密码已换密钥，-o BatchMode 免交互）
