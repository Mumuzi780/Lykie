# 构想-点击查词与端侧路线（2026-10-23 定稿）

> 状态：构思收敛完毕，**未出规格、未写代码**。本文是决策记录，防遗忘。
> 下一步：用户说「出规格」即动笔第①步。

## 一、问题起点（本轮讨论的动因）

1. 查词不能查短语：either...or... 这类分离式短语无法跳着选，只选 either 查不出短语义。
2. 手机端无法划词查词：Selection API 的原生行为（选择手柄、系统菜单）网页接管不了，默认弹浏览器自带选中提示而非 Lykie 气泡。

## 二、最终方案（桌面端交互）

### 手势设计（核心收敛点）

最初的「笔/手双模式 + 右键轮盘」构想，经讨论收敛为**无模式的手势分流**：

- **左键单击**：原生交互（划选、作答、点控件）——现状零改动。
- **右键 / 双击**：查词意图。二者并存，设置里各给开关（防右键被划词扩展劫持；双击天然选中单词，边界免费）。
- 无模式状态机、无切换成本、无切换遗忘问题。轮盘菜单搁置，未来模式多了（3 个以上）再考虑。

### 确认制短语联动（单次调用红线）

用户右键选中 either → AI **立即单次调用**，同时返回：短语释义 + 单词词典义 + 短语各段位置（either...or 的 or 在哪）。

- or 处做**引导性高亮**（虚线/浅色，视觉区别于用户主动选择）。
- 提示条：「点击 or 查短语 either...or ｜ 只查 either」。
- 点 or → 展示短语释义（结果已在手，**零二次调用**）。
- 点「只查 either」→ 展示词典义（同上零调用）。
- 用户改选别的词 → 旧引导清除，新流程开始。每次选中都有引导 = 智能感。
- AI 判断该词无短语关联 → 不出提示条，直接单词查词，保持安静。

**红线：AI 只在右键那一下调用一次，确认/回退全是本地交互。**

规格时待定细节：引导高亮在屏幕外时是否滚动定位（either 和 or 可能隔半屏）；短语跨段怎么处理。

### 作答不冲突

右键/双击查词不禁作答——左键作答、右键查词，天然分流。双击查词只在文本区启用（防双击落选项 button 先触发两次 click 作答）。

## 三、手机端方案

- **正文 tap = 查词**（点击单词，单词为整体单位）；控件 tap（挖空/选项/徽章）= 作答。命中分流与桌面共享同一套逻辑。
- 不用长按呼出轮盘（与系统放大镜/选择菜单打架）。轮盘在手机端后置。
- 需压制系统长按菜单：`user-select: none` + `-webkit-touch-callout: none`——等于全面接管选词，之后 Lykie 点击查词必须足够好，没有退路（这是手机端最大单点风险，实测把关）。
- 点击与滑动的区分交给浏览器 click 事件天然行为，不自写位移阈值。

## 四、调用设置页（后置）

- 用户提议：预设三档（省 token / 均衡 / 极致体验）+ 懂行用户自定义（调用次数、思考开关等）。
- **拍板：功能攒够之前不做**。现在只在代码里做铺垫——每个 LLM 调用点的参数收敛成常量（如 `LOOKUP_DISABLE_THINKING`），将来设置页上线时只是把常量来源从代码改成用户配置（纯接线）。
- 原则：自定义项必须对应真实存在的维度，不造空旋钮。

## 五、App 路线（用户真实反馈驱动）

- 背景：用户侧有真实反馈「手机端用户不用浏览器」，做 App 是产品成熟后的必然，只是时机问题。
- **拍板：不做原生、不做小程序**（前端重写 = 维护成本翻倍以上，单人不可承受）。
- **路线：Capacitor WebView 壳**——图标点进去是全屏网页，无地址栏，用户感知是 App，代码仍是现有站。日常迭代 95% 只碰网页层（与现在完全一样），维护成本约 +10~15%（新增的只是构建命令、商店过审 iOS 1-3 天、签名证书年度维护）。
- **PWA 是 App 的第一块地基而非替代品**：域名 + https + manifest + 图标 + 添加到主屏幕。将来 Capacitor 壳直接复用 PWA 的全部配置。裸 IP 不支持 PWA，需先买域名（几十块/年）+ Let's Encrypt 免费证书。
- 动手信号：手机端访问占比稳定成气候，或用户本人在手机上高频使用到忍无可忍。

## 六、落地顺序（定稿）

1. **桌面点击查词**：右键+双击并存（各带开关）+ 确认制短语联动（单次调用）。地基中的地基。
2. **手机端 tap 查词**：命中分流 + 系统长按菜单压制。
3. **调用设置页**：功能攒够后做，现在只做常量铺垫。
4. **PWA 地基**：域名 + https + manifest。
5. **App 壳（Capacitor）**：时机成熟时。
6. 轮盘菜单：模式 ≥3 个再考虑，可能永远不需要。

每步独立验收，遵守一次改一处的迭代纪律。

## 七、讨论中确立的技术事实（备忘）

- 划词与作答手势冲突的根治方案就是意图分离（本轮的手势分流），此前修的「选项点击守卫」是补丁不是终态。
- 双击浏览器默认选词 → dblclick 触发时选区现成，单词边界零成本。
- 扩展劫持右键无法压过（扩展在页面之上层级），只能提供双击/开关兜底。
- WebView 壳与浏览器跑同一套网页代码，点击查词方案本身无浏览器独占 API，天然可移植。
